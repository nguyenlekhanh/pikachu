# Zappy — AI live co-host

Zappy answers real TikTok LIVE chat and keeps the LIVE talking on its own, using the **active AI
provider** from Admin → AI Providers. Every conversational line is generated by that provider at
runtime: there is no canned dialogue list, no random canned picker and no simulated response.

In the default **always active host** mode Zappy also runs a watchdog that releases stuck requests,
busy flags and speech, a bounded priority queue, and an autonomous scheduler that starts a fresh
topic when the LIVE goes quiet.

The game, TikFinity, gifts, music, leaderboard and animations are unchanged. Zappy is a
conversational co-host only — it cannot change scores, the board, gifts or settings.

## Flow

```
TikFinity chat ──> ingest() ──> engine.handleChat()      (game commands, unchanged)
                        └────> AICohost.observeChat()   (never awaited)
                                   │  filter + score + batch window
                                   ▼
                             active AI provider (aiService.chat)
                                   │  decides + generates one JSON reply
                                   ▼
                        hub.broadcast('mascot', { ai:true, text, emotion, speechId })
                                   ▼
                     Zappy bubble + existing English TTS + music duck
                                   │
                     ws 'tts-state' (start | end | error | voices)
                                   ▼
                     AICohost.reportTts() -> honest SPEAKING / IDLE / ERROR
```

- The AI call is asynchronous and never blocks TikFinity ingestion, game moves or ticks.
- `aiService.chat()` resolves the active provider on **every** request, so switching from
  OpenRouter to Ollama in Admin takes effect immediately. Nothing in the mascot hardcodes a
  provider or model.

## Setting it up

1. Open **Admin → AI Providers**, verify the provider is CONNECTED and press **SET ACTIVE**.
   On first startup the imported OpenRouter provider is activated automatically when no provider
   was chosen yet; an existing admin choice is never overridden.
2. Open **Admin → AI Mascot** and press **TEST AI RESPONSE**. This sends a real request to the
   active provider and shows the actual generated line, provider, model and latency.
3. Keep chat/game/gift toggles on, set **Conversation frequency**, **Response cooldown**,
   **Max response length** and **AI temperature**, then **SAVE**. Settings are stored in the
   existing settings row and survive restarts.

`RESET GAME & SESSION` clears all conversation memory (messages, replies, topics, per-viewer
timestamps) for the new LIVE session; settings are preserved.

## What reaches the AI

Only a minimal, structured snapshot:

- game status, level, remaining tiles, total matches, auto-play flag
- top 3 leaderboard players and total player count
- last match (player, tile labels, points, combo) and last gift (name, coins)
- current viewer count, if TikFinity reports it
- recent filtered chat and recent Zappy replies (rolling window)

Never included: the board grid, player IDs, admin settings, API keys, tokens, file paths,
logs or private server data.

## Conversation selection

Zappy does not answer every message:

- Coordinates (`A1 B1`) and game commands (`TOP`, `ME`, `HINT`, `JOIN`, `RANK`, `HELP`) are
  ignored — they belong to the game engine.
- Duplicate text within 90 s and more than three messages per viewer per 15 s are dropped.
- Messages are scored for direct address (`Zappy`), questions, game/leaderboard topics, gifts,
  compliments and length, then collected in a **short batching window** (0.8 s high, 1.4 s normal,
  2.4 s low frequency).
- Up to three candidates are sent together, and the AI is explicitly instructed to return an
  empty reply when the message is spam, low value or not worth answering. The AI decides.

Controls that bound cost:

| Control | Behaviour |
|---|---|
| Response cooldown | Minimum seconds between spoken lines (3–180, default 8). |
| Frequency | Low/Normal/High changes batch window, event probability and quiet-chat threshold. |
| Max response length | Hard character cap applied before speech. |
| Temperature | Passed to the provider. |
| One in-flight request | Requests never run in parallel; anything else enters the bounded queue. |
| Queue | At most 6 pending turns, ordered by priority; the least valuable oldest turn is dropped first and a direct question is never dropped. |
| Retry policy | One retry for timeout/network/HTTP 5xx; empty or unusable answers are retried up to **Maximum retries** in always-active mode. |
| AI request timeout | Seconds before a request counts as stuck (5–90, default 20). |
| Context window | Last 4 chat turns, 8 recent replies and a capped context object. |
| Event commentary | Separate longer cooldown and probability; optional toggle. |
| Autonomous conversation | One topic per idle window (20–35 s by default), never during an active conversation. |
| Watchdog | Releases a stuck request, busy flag or speech and schedules a bounded recovery attempt. |

## Always active host mode

`aiAlwaysActive` (on by default) changes Zappy from "answer sometimes" to a host that always keeps
the stream alive:

- **No silent turn.** Empty content, whitespace, invalid JSON, a broken response shape, unusable
text and a repeated line are all rejected. The model is asked again with the real conversation
context and one instruction: produce one short, natural, entertaining line. Nothing from the
server is ever spoken as a fallback; if every attempt fails the failure is reported in Admin and a
recovery attempt is scheduled later with exponential backoff (8 s → 120 s, at most six attempts,
reset after any success).
- **Three sources of conversation:** viewer chat, real game/gift/leaderboard events, and autonomous
topics when nobody is talking.
- **Autonomous scheduler.** After an idle window of `aiMinIdleSec`–`aiMaxIdleSec` (default 20–35 s,
  randomised) Zappy makes exactly one AI request. It never interrupts a spoken line, never fires
  while a viewer conversation is active or a turn is queued, and the prompt forbids repeating a
  recent topic. The randomness is only in the timing; the content always comes from the provider.

### Priority

Direct questions to Zappy > viewer chat > gifts > game events > autonomous. Low-priority items are
bounded (6 entries, 20–60 s lifetime) so a burst of commentary can never bury a viewer question.

### Watchdog

`aiWatchdog` runs once a second and checks the in-flight request age, the busy flag, the queue,
the speech state and scheduled recoveries. Recovering bumps a request epoch, so a late answer from
the abandoned request can never be spoken, and it preserves the queue.

## Speech: what is actually true

The server cannot see the browser's speech engine, so the overlay reports real events:
`tts-state` with `start`, `end`, `error`, `skipped` and `voices`. Each line carries a `speechId`;
reports for any other id are ignored, which is what makes recovery and session resets safe.

- **SPEAKING** is shown only after the overlay confirmed that playback started. A broadcast alone is
  reported as `PENDING`.
- Completion and failure always release the busy state and restore the music bed
  (`music.restore()`); ducking still starts through `voice.speak → music.duckFor`.
- If the browser has no speech voices, Admin shows
  *NO SPEECH VOICES IN THIS BROWSER — the line would be text only* instead of pretending audio played.
- A line the overlay never played is reported as `skipped`, so the server does not wait for a
  completion that will never arrive.

## Personality

The persistent system prompt lives in `server/ai/personality.js`: cute, funny, energetic,
friendly, slightly mischievous, casual American English, short one-or-two-sentence replies,
no customer-support tone, no repeated greetings, no emoji/markdown/URLs (they are spoken aloud).

The model returns JSON:

```json
{"reply":"...","emotion":"happy|laughing|surprised|excited|sad|thinking|confused|neutral","reason":"..."}
```

`thinking` maps to the existing sleepy face, `confused` to surprised and `talking` to happy — no new
animation assets. The reply is sanitized (markup, URLs, emoji removed, length capped) before it is
shown or spoken.

## Safety and live chat

- Viewer messages are untrusted data, clearly labeled inside the prompt; the system prompt
  forbids following instructions found in them, revealing prompts/keys/admin data, or claiming
  admin/game powers.
- The server ignores any action the AI might suggest: the only side effect is a `mascot` broadcast.
  Points, leaderboards, gifts, game state and configuration remain engine/admin-only.
- Responses are sanitized and capped; family-friendly rules are in the prompt.
- Errors are redacted and stored in `aiCohost.lastError` for Admin → AI Mascot. On failure Zappy
  says nothing (no fallback line, no provider switch) and the game continues.

spam filtering, duplicate suppression, cooldown, disabled mode, sanitized provider failure with

in-flight requests, active provider switching, real test-response behaviour, session-reset memory
clearing, setting clamps/persistence, gift/match reactions and prompt sanitizing — plus the
always-active behaviour: empty answer retried, invalid JSON retried, all-retries-exhausted stays
silent, duplicate line replaced, timeout and unreachable provider reported, stuck request / busy
flag / speech recovered with the late answer dropped, bounded recovery backoff, TTS start/end/
error/skipped/voice telemetry, autonomous conversation with no comments, idle-window respect,

engine coordinates, and the TTS/music wiring between `voice.js`, `main.js` and `music.js`.

Run everything with `npm test`.

## Limitations

- Speech uses the browser's Web Speech API. OBS browser sources may ship without voices; open the
  overlay once in Chrome/Edge for reliable audio (see `docs/OBS_SETUP.md`).
- The AI provider must be reachable from the machine running this server. A local Ollama server
  must listen on the LAN (`OLLAMA_HOST=0.0.0.0`) and allow its port through the firewall.
- Autonomous conversation spends provider credits on a timer; switch it off (or raise the idle
  interval) if the provider is metered.
- A watchdog recovery cannot cancel a provider HTTP request that a local server already accepted;
  it invalidates the response so it is never spoken.
